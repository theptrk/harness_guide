# Level 4 — Harden the loop

## What broke

Level 3 lets exceptions from a tool escape the agent loop. Give its clock an invalid timezone:

```text
📝 you › Use get_current_time with the timezone Mars/Olympus.

tool › get_current_time({"timezone":"Mars/Olympus"})
call failed: 'No time zone found with key Mars/Olympus'
```

The model requested a function call, but the file contains no matching `function_call_output`. The turn cannot continue.

Level 4 handles two classes of failure differently:

- A tool failure becomes a `function_call_output`. The model can read it and decide what to do.
- An expected API or harness failure stops the program with a short error. Another model call cannot repair an exhausted API retry budget or an incomplete response.

Unexpected programming and persistence errors remain uncaught and produce a traceback. Hiding those errors would make the harness harder to debug.

The prompt-reading loop in `main()` keeps the same shape. This level configures the API client and hardens the work inside `run_turn()`.

```text
🤖 model › The request failed because `Mars/Olympus` is not a recognized IANA time zone. No current time could be retrieved.
```

The tool still failed. The loop did not fail.

## A tool error still completes the call

A normal message has no paired result. A completed `function_call` does: if that call is replayed in later model input, it needs one `function_call_output` with the same `call_id`.

```text
message
→ no paired item

function_call(call_123)
→ function_call_output(call_123)
```

The output is required whether the Python operation succeeds or fails.

`run_tool()` turns either outcome into a string. Its `try` block contains the operations that can fail because of the model-selected call:

```python
def run_tool(tool_call) -> str:
    try:
        arguments = json.loads(tool_call.arguments)
        tool_function = TOOL_FUNCTIONS.get(tool_call.name)
        if tool_function is None:
            raise LookupError(f"unknown tool: {tool_call.name}")
        return tool_function(**arguments)
    except Exception as error:
        return tool_error(type(error).__name__, str(error))
```

This catches malformed JSON, a name missing from the registry, arguments that do not match the Python function, and exceptions raised by the function. It does not catch failures from the API call, history file, or rest of the loop.

The caller receives either the successful value or structured error in `tool_result`, then appends the matching output:

```python
tool_result = run_tool(tool_call)

history.append_api_item(
    chat_file_path,
    {
        "type": "function_call_output",
        "call_id": tool_call.call_id,
        "output": tool_result,
    },
)
```

`append_api_item()` writes that output to the chat's JSONL file as replayable model input. On the next loop pass, `get_input_items()` includes both API items:

```text
function_call(call_123)
function_call_output(call_123, error)
```

The model can correct an argument, choose another tool, or explain the failure. Both items remain in later input for this conversation.

This rule applies to a completed function call. If the model response ends while a function call is still incomplete, the harness does not replay or execute that partial call, so it does not add an output.

`strict: True` constrains the JSON shape generated by the model. It cannot prove that a string names a real timezone. The Python function still validates that when it constructs `ZoneInfo(timezone)`.

## Bound the loop

Level 3 will execute tool calls until the model stops requesting them. Level 4 allows five:

```python
TOOL_CALL_LIMIT = 5
```

The previous level's exercise needs three tool calls. Five leaves room for two corrected calls while placing a concrete bound on tool execution. This is a budget for this tutorial, not a universal value.

When the model requests a sixth call, the harness returns a `ToolCallLimit` error without executing it. The next model call sets:

```python
tool_choice="none"
```

The model must answer using the results it already has. The limit therefore bounds executed tools rather than abandoning a `function_call` without its required output.

Try asking for the current time in six timezones. The sixth request should receive a `ToolCallLimit` result, followed by an answer.

If the model requests another tool despite `tool_choice="none"`, the harness stops the program instead of executing it.

## Check the response before executing it

An HTTP request can succeed while the model response has:

```json
{
  "status": "incomplete",
  "incomplete_details": {
    "reason": "max_output_tokens"
  }
}
```

The other incomplete reason is `content_filter`.

This is the first level where the JSONL file contains output that must be preserved but must not become later model input. Level 4 distinguishes the two cases by event type.

A completed API item is wrapped in a local `api_item` event:

```json
{
  "kind": "api_item",
  "item": {
    "type": "message",
    "role": "assistant",
    "status": "completed"
  }
}
```

`api_item` is a name used by this tutorial, not an OpenAI API type. Its inner `item` may be a user message, completed assistant message, `function_call`, or `function_call_output`.

Output from a non-completed response is stored as a different event:

```json
{
  "kind": "incomplete_item",
  "item": {
    "type": "function_call",
    "status": "incomplete"
  }
}
```

`history.get_input_items()` projects only `api_item` events into the next API `input` list:

```python
if entry["kind"] == "api_item":
    items.append(entry["item"])
```

The `incomplete_item` remains in the JSONL file for inspection. It is never replayed or executed. No separate boolean is needed; the event type carries that meaning.

The user item was written before the incomplete response and remains replayable in Level 4. After running this failure test, start a new conversation rather than continuing that file. Level 5 adds turn IDs so a failed or interrupted turn can be excluded as one unit.

The incomplete reason belongs to the response, not its output item. A separate local event preserves it:

```json
{
  "kind": "model_call_finished",
  "status": "incomplete",
  "incomplete_reason": "max_output_tokens"
}
```

The event stores only the response status and incomplete reason. That is enough to explain why the partial item was preserved. `get_input_items()` ignores this structural event.

Level 4 saves the response and outcome events, then calls `require_complete(response)` before looking for a tool call.

You can force the model to run out of output tokens:

```sh
printf '%s\n' 'What time is it in Tokyo?' |
  MAX_OUTPUT_TOKENS=16 uv run --env-file .env series-1/04-harden/main.py --new
```

One run produced an incomplete function call whose arguments ended at:

```json
{"arguments":"{\"timezone\":\"","status":"incomplete"}
```

The program stopped with:

```text
harness failed: model response incomplete: max_output_tokens; no tool from this response was executed
```

Executing that tool would require guessing the missing argument. Sending the identical model request again would use the same token cap. This level stops instead. A later design could raise the cap or continue partial answer text, but it must not execute a partial tool call.

Retrying after `content_filter` is also not useful without changing the request.

## API retries and timeouts

The client is configured explicitly:

```python
client = OpenAI(max_retries=2, timeout=30.0)
```

The SDK retries connection failures, request timeouts, rate limits, and selected server errors. Two retries means at most three attempts. If those attempts fail, the API exception stops the program with a short error instead of entering another agent pass.

The 30-second API timeout does not stop a Python tool. `get_current_time()` performs no blocking network or subprocess work, so it needs no separate timeout. A later HTTP or shell tool must set a timeout on that operation. A thread timeout only stops waiting for a function; it does not stop the function itself.

## What breaks next

The loop now handles tool errors, tool-call limits, and incomplete responses. Each model call still leaves the terminal unchanged until the complete response arrives.
